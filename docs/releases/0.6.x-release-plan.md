# 0.6.x implementation and sequential release plan

Decision recorded: 25 September 2026. This plan applies the approved
[public roadmap](../../ROADMAP.md) and [harness experiment](../agent-harness-experiment.md).
It is an acceptance and delivery contract, not evidence that planned capabilities have shipped.
Publication checkpoint: 0.6.0 was published and verified on 26 September 2026;
0.6.1–0.6.4 are planned. See the [0.6.0 release record](0.6.0.md).

## Delivery rule

Complete and publish **0.6.0, then 0.6.1, then 0.6.2, then 0.6.3, then 0.6.4**. Each milestone
must be usable within its complete stated scope through the supported CLI and SDK surfaces,
documented, validated, published to npm, and verified against its remote tags before the next
milestone is published. Do not accumulate all five milestones into a single release or move an
unfinished acceptance item to the next milestone while retaining a completion claim.

The user has authorized this sequence and use of the publishing script. A missing credential,
registry permission, failed check, publication conflict or platform dependency is a concrete blocker
to report and resolve; it is not permission to skip validation, rewrite a published version, or
claim an unpublished milestone is released. CI repair remains deferred. Local release checks and
single-publisher coordination are still required.

“Finished” never means “passed” by itself. In 0.6.1, execution may finish while task verification is
unavailable. In 0.6.2 onward, a verified task pass requires the declared observable outcomes; pending
approval must not become approval granted. Usage that cannot be measured remains unavailable.
Do not present a pre-request token check as an absolute financial cap or cancellation as rollback.

## Native first; optional integrations separately

Implement and qualify the shared native execution interface in 0.6.1 before adopting optional
harnesses. AI SDK is the first integration, Pi the second with strict original-argument enforcement,
and fx remains experimental until stock provider transport and host cleanup are qualified. These
integrations can receive separate package releases without delaying the native milestone. Their
release notes must map to the compatible milestone contract without inventing a completed next
milestone. A package patch is not automatically a roadmap milestone.

For each integration, verify declared tool authority, strict validation/explicit repair policy,
fresh environment, cumulative budgets and missing usage, complete call/error events, cancellation,
supported runtime/packaging, version/configuration identity and unsupported-feature reporting.
Resume conformance becomes required when the integration claims 0.6.3 resume support. Avoid loading
optional dependencies on the default CLI path. No fork or wholesale agent-framework migration is
part of the approved baseline; first exhaust supported extension points.

The experiment proves specific integration behavior with shared wrappers and fixture transports.
It does not qualify stock hosted-provider paths or show task-quality uplift: all 48 selected local
model trials failed structured tool use. Production adoption needs its own bounded qualification.

## Versions, manifests and tags

Packages retain the repository's independent Changesets versioning. Do not bump every package to
`0.6.x` merely to match the milestone label. Select direct package bumps from actual public changes;
include necessary downstream dependency updates and runtime compatibility fixes.

For every milestone, retain a version-controlled JSON manifest at `docs/releases/<version>.json`
and a human-readable release record containing:

- Milestone version and `v0.6.x` annotated tag pointing to its final validated release revision.
- Exact newly published npm package names and versions in the JSON `packages` array, with matching
  Changesets package tags (`@artemiskit/<name>@<version>`). Document unchanged supported dependencies
  separately in the human-readable record; their older tags must not be moved to this revision.
- Source revision, supported Node/Bun versions and entry points, artifact/schema compatibility,
  included capabilities and explicit exclusions.
- Exact build, test, typecheck, lint, package-consumer and applicable runtime commands/results,
  known baseline warnings, bounded local-model results, and unverified platforms/providers.
- Registry availability/install verification and remote tag verification, with unresolved partial
  publication clearly marked until reconciled.

The milestone tag identifies a coherent public capability release; package tags identify the
immutable versions npm consumers install. Neither substitutes for the other. Never overwrite an
existing npm version or move an existing remote tag to conceal a correction; issue the necessary
package fix and document its relationship to the milestone.

The release verifier consumes that manifest at each gate (substitute the milestone being released):

```sh
bun scripts/verify-release.mjs local docs/releases/0.6.0.json
bun scripts/verify-release.mjs prepublish docs/releases/0.6.0.json
bun scripts/verify-release.mjs registry docs/releases/0.6.0.json
bun scripts/verify-release.mjs tags docs/releases/0.6.0.json
```

`local` checks the package map against the versioned checkout. `prepublish` additionally verifies
every preceding-manifest package on npm and its annotated remote tag against the preceding milestone
tag for 0.6.1 onward. It also rejects unpublished workspace versions omitted from the current manifest.
It rejects current release tags already pointing at another revision before npm publication.
`registry` verifies exact published versions and their `latest` dist-tags; `tags` verifies package and milestone remote tags against the released
revision. These checks complement actual fresh-consumer installation, behavior tests and release
notes. A successful metadata query alone does not prove the package runs.
Run `tags` from the release revision; later documentation commits intentionally do not move the
immutable release tags. Use `completed` to verify a historical milestone from a newer checkout.

After a milestone is fully published, independent non-core package releases use
`./scripts/publish.sh --publish-only --package-release`. This runs the `completed` gate on the
current core milestone: every recorded npm version and annotated package/milestone tag must already
exist at the original milestone revision. It does not require those historical versions to remain
`latest` or rewrite their manifests/tags. A newly advanced core milestone cannot use this path until
its own publication is complete. Independent releases still need their own exact package records,
fresh-consumer checks, registry verification and package tags.

Metadata gates cannot prove an existing npm payload equals the candidate build. On partial-release
retries, reconcile published tarball integrity/content with the retained candidate tarballs and
source revision before continuing. Never use the presence of a version alone to authorize replacing
its source or assigning a different tag.

## Release gate for every 0.6.x milestone

1. **Settle scope.** Check the relevant acceptance criteria and downstream consumers. Update the
   roadmap, guides, examples, migration notes and release limitations to match implemented behavior.
   Preserve legacy scenarios/artifacts and distinguish research tools from production interfaces.
2. **Prepare the exact package revision.** Add a scoped changeset, apply independent version bumps,
   review dependency/changelog changes, and commit the intended versioned release. Maintain a clean
   worktree and reproducible lockfile. Inspect complete diffs for unrelated/generated/secret content.
   Use `bun run version`, which also synchronizes Bun workspace-version metadata. Bun 1.3.10 can
   retain old versions after ordinary installation; packing then selects stale internal dependencies.
   If Changesets was invoked directly, run `node scripts/sync-workspace-versions.mjs` before packing.
3. **Run integrated local checks.** Use `bun install --frozen-lockfile`, `bun run build`,
   `bun run typecheck`, `bun run lint`, and `bun test` on the final revision. Add milestone-specific
   fixture, sandbox, checkpoint or report checks. Record known warnings and actual failures honestly.
   CI repairs are not included; failed required local checks still block publication.
4. **Test the distributions.** Pack the affected packages with resolved internal dependencies;
   inspect package contents and install the exact tarballs together into a fresh consumer outside
   the workspace. Run CLI help/authoring/validation or execution appropriate to the milestone,
   SDK/core imports and TypeScript consumer compilation. Test declared Node/Bun runtime entry
   points; repository-local module resolution must not hide missing exports/files/dependencies.
5. **Record bounded runtime evidence.** Follow the workflow guide's local Ollama compatibility
   checks using safe fixtures and recorded timeouts. Keep failures, unsupported tool protocols and
   unavailable measurements visible. Use deterministic provider/transport fixtures for reproducible
   contract acceptance; an advertised tool-capability flag is not a passed live tool round trip.
   Paid-provider calls are not required by this release plan without a separately bounded budget.
6. **Publish through the maintained script.** Run `./scripts/publish.sh --preflight`, then use
   `./scripts/publish.sh --publish-only` on already-versioned, clean `main` with no pending changesets.
   Never put credentials in a command, artifact or release record. Coordinate with the existing
   main-branch release workflow so only one publisher acts on the revision; do not repair unrelated
   CI or race a running publisher. The script's checks do not replace fresh-consumer verification.
   For the 0.6.x core line, the script requires the matching JSON release manifest and runs the
   local/prepublication gates before publishing, then the registry gate afterward.
7. **Verify npm before closing publication.** Query every expected package/version, install from
   the registry into another clean consumer, and rerun the public-surface smoke tests. If publication
   is partial, reconcile exactly those versions and dependencies before proceeding; do not silently
   skip a failed package or rebuild a different payload under an existing version.
8. **Synchronize the release.** Push the validated release commits and package tags, create/push
   the milestone's annotated `v0.6.x` tag, and publish release notes with the exact package map and
   evidence. Check remote tag targets against local commits and npm versions. Non-interactive
   `publish.sh` does not perform the Git push automatically.
9. **Close, then advance.** Mark the milestone released only after registry install and remote
   verification. Capture final Git state and any limitations. Start the next milestone from this
   published baseline; repeat all applicable gates for each subsequent 0.6.x increment.

The current script's `--dry-run` skips npm publishing but can still apply versions and create a
commit. It is not a read-only inspection command. Use package packing for distribution inspection
and the reviewed, already-versioned `--publish-only` path for publication. If the script changes,
verify its behavior before updating these instructions.

## Completion record

For each milestone, retain its release record under `docs/releases/`, link it from the roadmap,
and report: implemented scope, exact validations/results, package versions, npm verification,
release commit/tag, remote synchronization, dirty state, known limits and next milestone scope.
The existing [0.6.0 validation record](0.6.0-validation.md) describes source validation; packaging and
registry evidence must be added by the release owner before it establishes a published release.

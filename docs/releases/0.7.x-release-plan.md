## Delivery rule

Complete and publish **0.7.0, then 0.7.1, then 0.7.2, then 0.7.3**. The 0.6.x delivery rule applies
unchanged. Each milestone must be usable within its full stated scope through the supported CLI and
SDK, documented, validated, published to npm, and verified against its remote tags before the next
milestone is published. Do not accumulate milestones. Do not move an unfinished acceptance item to a
later milestone while still claiming the earlier one is complete. Do not label work released that
has only been implemented.

## Prerequisites before 0.7.0 publication

1. **Generalize the release verifier.** Accept `0.7.x` manifests (and later lines) instead of
   `0.6.x` only. Derive `previous` from the published milestone sequence so 0.7.0 names 0.6.4. Keep
   the immutable-tag, preceding-publication and core-version checks unchanged. Add tests for the line
   transition and for rejecting a skipped milestone.
2. **Fix the runtime used for release checks.** CI's `setup-bun` uses `latest` (currently 1.4.x),
   while the 0.6.x releases were validated on Bun 1.3.10. Record the Bun version used for each gate.
   Run the fresh-consumer checks on both Node and Bun as before.
3. **Track the CI outage.** GitHub Actions resumes once the billing lock is resolved. Restoring it
   isn't a release prerequisite, but the Release workflow will then open a Changesets “release
   packages” PR for any pending changesets. Coordinate so that only one publisher acts on a revision.

## Decisions

All four were approved as proposed on 19 November 2026. The paid-provider choice (3) resolved to
local-endpoint qualification only, stated as a release limitation, because no provider list or USD
cap was approved.

1. **Scope mapping.** Approve releasing the already-implemented live-control, summary and
   compatibility contract pieces with 0.7.0, while milestones 0.7.1–0.7.3 close only on their exit
   criteria (table above). The alternative is to hide those pieces until their milestone, which
   would mean removing exports that are already accepted.
2. **Surface naming.** Proposed CLI group `akit experiment` (`validate`, `run`, `report`), matching
   `akit workflow`. SDK functions would mirror the CLI.
3. **Paid-provider qualification for 0.7.3.** Choose either a bounded paid run (approve providers,
   models and a USD cap) or local-endpoint qualification only, stated as a release limitation.
4. **Concurrency.** Keep the manifest's concurrency fixed at 1 throughout 0.7.x (current contract),
   or schedule parallel execution as an explicit 0.7.3 item.
   *Superseded on 19 November 2026:* the user pulled the planned 0.7.3 parallel-execution item
   forward. A manifest may declare concurrency from 1 to 8, and live runs above 1 need an
   approval naming the level. Attempts are admitted against declared per-attempt reservations,
   so admission never commits more than a declared budget. With a budget sufficient for a serial
   run, concurrency never loses work; with an insufficient budget, which coordinates are
   measured may depend on timing, and the stop is recorded. The parallel level and the
   reproducibility caveat (completion order, and sampled outputs that may differ from a serial
   run under server batching even with fixed seeds) are stated on every result and report.

## Completion record

For each milestone, keep its release record and JSON manifest under `docs/releases/`, link them
from the roadmap, and report: implemented scope, exact validations and results, package versions,
npm verification, release commit and tags, remote synchronization, known limits and the next
milestone's scope.

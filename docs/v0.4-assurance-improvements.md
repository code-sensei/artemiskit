# Assurance improvements after v0.4

v0.4 establishes a necessary boundary: an invalid or incomplete measurement must not be reported
as an ordinary model failure or improve an outcome rate. This document turns that foundation into
the next implementation backlog for ArtemisKit as a trustworthy, scenario-based AI assurance test
runner.

It complements the public [roadmap](../ROADMAP.md). It is intentionally technical and does not
make legal-certification, compliance-certification, or universal model-ranking claims.

## Product standard

An ArtemisKit assessment should be able to answer the following for a named workflow:

> Given this target configuration, scenario/profile, policy, language, budget, and execution
> environment, what evidence supports or limits fitness for use?

The answer must preserve strengths, failures, unavailable capabilities, invalid measurements, and
method limits. A single context-free "best model" score is not sufficient evidence.

## Immediate v0.4.x hardening

These items improve the integrity release without changing its core purpose. They should be
separate, backward-compatible patches where possible.

| Priority | Improvement | Why it matters | Acceptance evidence |
| --- | --- | --- | --- |
| P0 | Apply the same redaction policy to evaluator reasons and bounded evidence as to target inputs/outputs. | A custom evaluator or judge reason can still contain customer or sensitive text. | Tests prove secrets and configured redaction patterns cannot enter manifests, storage, JSON, HTML, Markdown, or JUnit evidence. |
| P0 | Validate artifact and evidence payloads at runtime before serialization and storage. | TypeScript types alone cannot protect consumers from malformed custom-evaluator data at runtime. | Versioned parser accepts supported manifests, rejects malformed new evidence, and preserves documented legacy loading. |
| P0 | Test migration `003_evaluation_integrity.sql` against a disposable Postgres/Supabase instance. | Unit mocks do not prove SQL syntax, backfills, constraints, or index creation on a real database. | Migration-up test covers populated historical runs/cases, upgrade result, and queryability of integrity counts. |
| P0 | Add a release workflow preflight that proves npm credentials and package ownership before a versioned source release is announced. | A source version that cannot be published creates avoidable ambiguity. | CI has a non-publishing auth/ownership diagnostic and the release record distinguishes source-ready from registry-published. |
| P1 | Use distinct CLI and report treatments for `passed`, `failed`, `invalid`, `error`, and later `unavailable`. | Status words alone are too easy to miss in an operational assessment. | Snapshot/accessibility tests show unambiguous labels, icons/text alternatives, counts, and denominator on every supported surface. |
| P1 | Publish a strict-judge assurance example. | Existing users need a clear migration path from permissive legacy grading to strict measurement. | Example includes strict JSON rubric, malformed-response fixture, valid failure, evaluator failure, and report output. |
| P1 | Record release-validation results as an artifact. | A repeatable fixture suite is more useful when the exact revision, command, skips, and redaction review are saved. | A checked-in or attached release-candidate record follows [RELEASE_VALIDATION.md](../RELEASE_VALIDATION.md). |

### Status taxonomy follow-up

v0.4 exposes `passed`, `failed`, `invalid`, and `error`. Before adding more values, define a
stable taxonomy shared by executor, artifact, storage, CLI, SDK, and reports:

- `passed` and `failed` are valid evaluations and are the only statuses used for outcome rates.
- `invalid` means the measurement could not establish a valid result, such as malformed strict
  judge output or an invalid evaluator result.
- `error` means target or execution infrastructure failed after an attempted run.
- `unavailable` should be considered only when the system can positively identify an unsupported
  target capability or intentionally unavailable measurement before execution. It must remain
  outside the valid-outcome denominator.

Every non-valid status needs a bounded machine-readable category and a human-readable sanitized
reason. Do not collapse categories merely for a simpler chart.

## v0.5: reproducible evidence and comparison eligibility

The next substantive release should make evidence reviewable and comparisons defensible.

### Workload and rubric identity

Add content-derived, versioned identities for the scenario workload, rubric/evaluator settings,
assessment profile, policy controls, fixture set, and reviewed pack. A comparison must declare
which identities match and which differ.

Identity inputs must exclude secrets, raw credentials, and volatile fields that make equivalent
runs look different. A digest indicates matching inputs; it is not a cryptographic attestation of
the target provider's behavior.

### Execution provenance

Persist bounded, redacted evidence for:

- requested provider/model and observed model identity when the provider returns it;
- target versus evaluator/judge model, configuration, and usage separately;
- generation settings, adapter version, runner version, scenario/profile/rubric identities;
- attempt, retry, and independent-repetition identities;
- execution time, relevant environment constraints, declared tool permissions, and fixture version;
- cost inputs with source and timestamp, or an explicit `unavailable`/user-supplied designation.

### Comparison contract

Comparisons and baselines must refuse or qualify results when workload, rubric, policy, profile,
language, target configuration, or execution mode differs. A dashboard should show "not directly
comparable" rather than fabricate a delta. Repetitions, retries, skipped work, and invalid/error
measurements must remain visible in aggregates.

## v0.6: native agent harness

For real-world assurance engagements, a prompt-only runner is insufficient. ArtemisKit needs a
provider-neutral native harness for configurable tool-using agents.

### Required scenario controls

An agent scenario should declaratively specify:

- target adapter, system instructions, conversation/state fixtures, and input data;
- permitted tools, schemas, authority boundaries, and side-effect policy;
- network, filesystem, container/MCP, time, step, token, and cost budgets;
- controlled fault injections: absent tool, stale data, malformed result, timeout, conflicting
  instructions, and bounded retry behavior;
- required final state, produced artifacts, tool trace expectations, and independent acceptance
  checks;
- redaction, retention, and evidence limits for prompts, state, traces, and tool results.

The harness should fail closed for undeclared authority. Fixture-backed and disposable execution is
the default; live systems, customer data, and paid model calls require explicit authorization,
bounded credentials, and a run budget.

### Independent scoring

Do not accept an agent's statement that it completed work as proof. Score observable outcomes:
validated files/records, simulated state changes, schemas, policy checks, tool traces, and final
state. Distinguish task failure, policy violation, target error, evaluator invalidity, and
unsupported capability.

## v0.7: provider-neutral comparative execution

Generalize repeated benchmark orchestration into a provider-neutral experiment contract.

- Run a declared compatible workload against multiple configured targets.
- Separate one-shot scenario cases from multi-turn agent workflows while giving each a compatible
  experiment identity.
- Make retry policy, repetitions, seeds where applicable, concurrency, time budget, and excluded
  cases explicit.
- Report results by model, workload, policy/control, language, task type, and operational metric;
  never only by a global average.
- Document sample sizes and assumptions for any confidence or uncertainty calculation.
- Gate live paid-provider runs behind explicit approval and cost budgets.

## v0.8: assessment profiles and reviewed packs

Profiles turn customer needs into executable requirements. A profile should cover capability,
security, language, latency, cost, organizational policy, escalation, data handling, tool
authority, and critical-failure rules.

Start with reviewed packs for customer-service and logistics workflows, then prioritize regulated
or moderately regulated domains such as financial services, health, insurance, public sector,
education, telecommunications, and energy. Each pack needs owner, version, source/rights,
intended use, prohibited claims, language/region coverage, known gaps, rubric, policy controls,
and review history.

Framework mappings (for example, GDPR, NDPR, NIST AI RMF, or Nigerian AI guidance) should map
testable technical controls to assessment evidence. They must state coverage limits and required
human legal, privacy, security, and domain review. ArtemisKit must never represent a technical
test pass as regulatory certification.

## v0.9: reports, release gates, and leaderboard

Reports should regenerate solely from saved, sanitized evidence and disclose methodology,
coverage, model/configuration identity, scenario/profile/rubric versions, valid-rate denominator,
invalid/error/unavailable counts, exclusions, and limitations.

The future public leaderboard must be scenario-first:

- Filter by workflow, sector, language/region, capability, policy outcome, operational constraint,
  and model/configuration.
- Require approved public data, reproducible workload identities, sample size, method, date, and
  known limitations for every entry.
- Show incomplete and unavailable measurements rather than silently omitting them.
- Do not convert heterogeneous customer assessments into a universal model ranking.

CI release gates should consume the same profile/evidence contract as reports, with explicit
thresholds, critical-failure rules, approved exceptions, and regression compatibility checks.

## Delivery and validation discipline

Each increment should contain the contract, serialization/storage changes, all consuming surfaces,
documentation, compatibility fixtures, and release-validation cases in the same reviewable change.

Before a release, run the applicable deterministic cases in [RELEASE_VALIDATION.md](../RELEASE_VALIDATION.md),
full tests, typecheck, lint, build, migration tests where relevant, and a final artifact/redaction
review. Live provider work is supplementary evidence only and must identify approval, budget,
model configuration, and nondeterministic limitations.

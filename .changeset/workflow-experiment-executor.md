Add `createWorkflowExperimentExecutor`, the built-in executor that runs `agent_workflow` tasks through the native workflow engine with a host-supplied client per target. Each attempt verifies the SHA-256 of the exact workflow bytes before parsing, parses without `${VAR}` expansion, inlines a file `initial_state` fixture resolved under the workflow's directory, and runs only in the workflow's declared `simulated` or `sandbox` environment with network denied. The coordinate's target replaces the workflow's provider and model. The metadata-only workflow record is the evidence (`workflowRecordIdentity`), and it never contains model text or fixture content. Policy denials and exhausting the workflow's own budgets are `policy_failed`; transport, deadline, environment and cleanup failures are `infrastructure_failed`; a truncated response is `invalid` (`response_truncated`). Workflows with semantic outcomes are refused, because experiment runs configure no independent judge. The executor declares the workflow's request limit as its per-attempt demand, so concurrent runs can admit it.

Workflow tasks honour the same per-target generation settings and per-repetition seed as scenario tasks: `temperature`, `top_p`, `presence_penalty`, `max_output_tokens` and the coordinate's seed are sent with every workflow model request, and `reasoning_effort` is recorded (the target's client sends it). `top_k` and `min_p` are still refused (`generation_setting_unsupported`), because no request transport sends them. To support this, workflow sessions accept host-bound `generation` options (`topP`, `presencePenalty`, `seed`, `reasoningEffort`), and workflow records list every value sent in `configuration.generation`. Workflows run without these options send and record exactly what they did before.
